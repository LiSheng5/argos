## 0. 待解的缺陷清单

| # | 缺陷 | 现状 / 实测表现 |
|---|---|---|
| D1 | 教训**只能被强化、不能被证伪** | 已补 `weaken()`（反证削弱），但规则粗糙 |
| D2 | 反证规则粗糙（走通一次就降一级） | 未验证过 |
| D3 | 复核是**固定周期**（`revalidate_every=2`），非最优 | 只扫过 2 这一个值 |
| D4 | **归因粒度粗**：把失败记到整条路线 | 实测踩到"绕路被挡 → 把绕路也禁掉 → 无路可走" |
| D5 | 阈值 / 周期**全靠拍** | `min_hits=2`、`confidence≥0.6`、`revalidate_every=2` |
| D6 | 教训降到 0 就**删除**，无审计、只在内存 | 删了就查不到历史 |
| D7 | **没有独立的 Evaluator** | 判分逻辑内嵌在 Simulator 的 `ActionResult` 里 |
| D8 | 场景集**区分不出成功率** | 四/五组配置成功率都是 89.4% |

## 1. 最直接对应：ExpeL —— 经验即自然语言洞察，带投票与淘汰 ✅

**ExpeL: LLM Agents Are Experiential Learners**（Zhao et al., AAAI-24, arXiv:2308.10144）

从原文（v3 §4.2 "Learning from Successes and Failures"）核实的机制：

- 四个操作：**ADD / EDIT / UPVOTE / DOWNVOTE**；
- 新洞察的 **importance count 初始 = 2**；
- **UPVOTE / EDIT → 计数 +1；DOWNVOTE → 计数 −1；计数归 0 → 移除该洞察**；
- 论文给这个设计的目的（原文）：*"This particular design choice robustifies the process since
  even successful trajectories can be suboptimal and mislead the generated insights."*
- 提取素材是**失败/成功轨迹对**，或一批成功轨迹 —— 即**对比**而非只看失败。
- 效果：ALFWorld 59% vs ReAct 40%；HotpotQA 上用单次尝试达到 Reflexion 多次尝试的水平。

**对我们的意义**：我的 `hits`（初始 = `min_hits` 2，反证 −1，归 0 撤销）**与它几乎同构** ——
等于独立的论文验证了这条设计方向。可借两点：

1. **EDIT 操作**：我现在只会"降级/删除"，但很多情况下正确动作是**把教训改准**
   （例："北线不能走" → "北线在**工作日上午**不能走"）。EDIT 比删除信息量大得多。
2. **成功/失败成对喂给提取器**：我现在只在失败时记录；ExpeL 用**对比**来生成洞察，
   这天然抑制"从单条轨迹过度泛化"。

## 2. 复核节奏：这本质是非平稳多臂老虎机（NS-MAB）✅

"环境会变，旧经验会过期"在 RL 里是成熟问题，有两族标准解法：

| 族 | 代表算法 | 机制 |
|---|---|---|
| **被动遗忘**（不问"变没变"，只淡忘） | Discounted UCB、Sliding-Window UCB（Garivier & Moulines 2011）、**SW-TS**（Trovò et al. 2020，arXiv:2409.05181） | 只保留最近 W 次观测 / 对旧观测乘折扣 |
| **主动遗忘**（检测到变化才重置） | CUSUM-UCB、**GLR-klUCB**（Besson & Kaufmann 2019）、REXP3、**ADWIN 系（ADS-TS / ADR-TS）**、Page-Hinkley（Adapt-EvE） | 变点检测 → 收缩窗口或重置统计量 |

**对我们的意义**：我的 `revalidate_every=2` 其实是 **REXP3 那种"周期性重启"的最粗版本**。
两个更好的替代：

- **换被动遗忘**：给教训加**折扣/滑窗** —— 旧证据自然淡出，不需要显式试探。
  实现上几乎就是把 `hits` 改成"带折扣的计数"，比现在的"每 2 轮试探一次"更平滑。
- **换主动遗忘**：**ADWIN / 变点检测** —— 只在"数据分布真的变了"时才失效旧教训。
  优点是不浪费试探动作；代价是要引入检测器（有现成轻量实现，stdlib 可写简化版）。

## 3. 归因本身就不靠谱：Who&When ✅

**Which Agent Causes Task Failures and When?**（Zhang et al., ICML 2025 **Spotlight**,
arXiv:2505.00212, PMLR v267）

- 首个自动化失败归因基准 **Who&When**（127 个多智能体系统的失败日志，人工标注 Who / When / Why）；
- 最好方法：定位责任 agent **53.5%**，定位**决定性错误 step 只有 14.2%**，有的方法**低于随机**；
- 即使 o1 / DeepSeek R1 也不达实用水平。

**对我们的意义（这条最重要）**：**"这次失败是因为北线"本质上是一个未被验证的假设** ——
归因这件事在学界都还很不可靠。所以正确的工程反应不是"把归因做准"，而是：

1. **让教训可撤销**（已做）—— 归因错的时候能退回来；
2. **让教训可审计**（未做，见 D6）—— 人能看见 agent 到底学到了什么；
3. **用干预验证代替纯推理**（见下）。

## 4. 干预式验证：DoVer（Do-then-Verify）✅（二手描述，机制清晰）

来自 Fourney et al. 2025 的 **DoVer** 思路（经一手论文的二级转述，
核心主张可核对）：*"prior attribution methods infer a failing step from the log alone,
which remains an untested hypothesis unless validated by execution"*。

做法：**假设责任步骤 → 在该点做最小修改 → 重跑 → 看结果是否变好**，
从而**验证或推翻**归因，而不是靠日志猜。

**对我们的意义**：我的"周期试探"其实就是它的简化版（试探 = 干预 = 重跑）。
可以正规化成：

- 复核从"**定期**"改为"**按需 + 干预验证**"；
- 每次试探都**记录假设与结果**（"我假设北线恢复了 → 走一次 → 成功 → 削弱教训"），
  于是教训带上了**验证历史**，而不只是一个计数。

## 5. 三角色分工：Reflexion ✅ + 一个反直觉的负结果 ✅

**Reflexion**（Shinn et al., NeurIPS 2023, arXiv:2303.11366）

- 结构是**三个角色**：Actor（执行）/ Evaluator（判分）/ Self-Reflection（写教训）；
  抽象明确说反馈可来自**外部或内部模拟**，形式可以是标量或自然语言；
- HumanEval pass@1 91% vs GPT-4 80%。

⚠️（二手一致，未回原文）反思记忆是**有界滑窗，上限约 1–3 条**；在 WebShop 这类
动作空间宽而模糊的任务上**卡在局部最优、反思失灵**。

**另一个必须知道的负结果**（多篇二手引用 Huang et al. 2023）：
**没有外部反馈的"自我纠错"平均会让性能掉 1–5%** —— 模型会把对的改错。
→ 这正好解释为什么我们的"削弱"必须由**外部证据**（试探真的走通了）驱动，而不能靠 LLM 自省。

**对我们的意义**：把 **Evaluator 显式独立出来**（D7）。现在判分逻辑隐在 Simulator 里，
"谁在说这次失败了"这件事不可配置；独立之后才能做"多评估器/更严评估器"的对比实验。

## 6. 记忆工程：不删、只失效（可审计）⚠️

开源记忆框架的横向对比（二手综述，未逐个回原文）：

| 方案 | 存储 | 遗忘策略 |
|---|---|---|
| **Zep / Graphiti** | **时序知识图谱（bi-temporal）** | **Invalidate 不 discard** —— 标记失效、保留全留痕 |
| Mem0 | 向量 + 图 | 动态遗忘（低相关性衰减） |
| Letta / MemGPT | 三层（Core / Recall / Archival） | Agent 自主管理（不可控） |

Zep 的设计要义：每个事实带 `created_at / updated_at / source`，
**据此判断"是否需要重新确认"** —— 这正好是 D6 + D3 的工程化答案。

**对我们的意义**：教训**不要删**，改成 `status = active | invalidated`，
保留 `created/updated/source/验证历史`。审计与复核都有据可依。

## 7. 可借方案排序（按"收益 ÷ 成本"）

| 优先级 | 借什么 | 治哪条 | 成本 |
|---|---|---|---|
| **P0** | 教训改成 **invalidate 不删除** + 记录验证历史 | D6 D4 | 低（纯数据结构） |
| **P0** | **EDIT 操作**：把教训改准，而不是只降级/删除 | D2 D4 | 低 |
| **P1** | 复核从"定期"换成 **折扣/滑窗（SW-TS 风格）** | D3 D5 | 中（改计数为折扣累计） |
| **P1** | **成功/失败成对**喂给反思（对比而非只看失败） | D1 D2 | 中 |
| **P2** | **Evaluator 独立成模块** | D7 | 中（重构接口） |
| **P2** | **变点检测（ADWIN 简化版）**替代固定周期 | D3 D5 | 中高 |
| **P3** | 场景集补"单次运行救不回来"的类型 | D8 | 低（但要想清楚） |

## 8. 明确**不**借的 / 借了也未必有用的

- **不引入 LLM 做归因/反思的判分**：Huang et al. 的负结果 + Who&When 的低准确率都说明
  "让 LLM 自己判断学到什么"风险大。本项目的红线仍是**LLM 只提议、代码决定执行**。
- **不引入 bandit 的全套理论实现**：我们只有 2 条路线、确定性世界，
  上 Thompson Sampling 的收益有限；**折扣计数**已能拿到大部分好处。
- **Reflexion 的"多轮重试"不适合我们**：它靠"再试一次"刷 pass@1；
  我们的场景里重试有真实代价（动作数/时间），所以衡量的是**代价**而非单纯成功率。
- **别把"反思一定有用"当结论**：本仓库 benchmark 已经实测出
  「反思只写不读 = 零价值」的负结果；上面这些方案里，**只有能被自己的 benchmark 验证的才值得上**。

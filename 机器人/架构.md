> 更新：2026-08-28。接续 可行性调研.md。本文件是机器人版顶层架构：复用接缝、robot/ 目录、RobotExecutor、运动原语白名单与安全闸门、感知/语音、sim2real 验证。最小闭环已实现（brain.py，见 §9）。

## 1. 复用边界一句话
**三角色决策 + 落账口 + 记忆 = 原样复用（大脑）；"动作出口"抽成 ActionBackend，机器人侧换成 RobotExecutor（执行器）；A 审查从"游戏白名单"升级为"真机安全闸门"。**

| 层 | 位置 | 复用/新建 |
|---|---|---|
| B1 对话 · B2 编译 · A 审查 | npc/reviewer.py | 复用 |
| 落账口 book() · pending_task 语义 | npc/npc.py | 复用 |
| 记忆三阶段（反思/关联/遗忘） | npc/memory.py + npc/npc.py | 复用 |
| 动作出口（原 apply_action(world,...)） | 抽成 ActionBackend | 改接缝（默认=游戏） |
| 执行器 | robot/executor.py | 新建 |

| 语音入（ASR）+ 出（TTS） | ASR 新增；TTS 复用 npc/tts.py | 各半 |
| Web 服务形态 | npc/server.py | 复用模式：只换注入 |

## 3. 复用接缝：ActionBackend
大脑只管"决定做什么"（move/gather/deliver/...），不关心动作落在游戏世界还是真机身上。原代码在 npc/npc.py::run_task 与 scheduler 里直接调 npc.world.apply_action(world, ...)。最小改动是给 NPC 注入一个动作后端：
```
class ActionBackend(Protocol):
    def observe(self) -> dict: ...
    def apply(self, action: str, params: dict) -> tuple[bool, str]: ...
class GameBackend(ActionBackend):
    """游戏后端 = 现状：直接改世界字典 apply_action。"""
```
- 默认 GameBackend，游戏 NPC 行为零回归（用同一套测试守住）。
- 机器人 RobotBackend 把 move/gather/deliver 转发给 RobotExecutor。
- 落账口语义不变：book() 仍是唯一生 pending_task 的入口；承诺成立 = 被推进活动队列，只是"推进"到执行器而非世界字典。

## 4. RobotExecutor
```
# executor.py 里是普通类（鸭子类型）而非 Protocol —— 没有 isinstance 校验，
# 任何实现了这几个方法的对象都能注入。接口签名以本文件为准。
class RobotExecutor:
    def move_to(self, x, y, yaw) -> bool: ...
    def navigate(self, waypoints) -> bool: ...   # 供"走到房间/巡检"
    def grab(self, target: str) -> bool: ...
    def release(self) -> bool: ...
    def pose(self) -> dict: ...                  # x,y,yaw,电量,imu,急停态
    def estop(self) -> None: ...                 # 必须实现：让正在跑的长动作能中途退出
    def clear_estop(self) -> None: ...           # 解除急停（缺了就解不开，接单永远被拒）
class SimEntity(RobotExecutor):
    """仿真执行器：unitree_mujoco（真实物理仿真）/ stub（无 3D 先跑链路）。"""
class UnitreeReal(RobotExecutor):
    """真机执行器：unitree_sdk2 / unitree_ros2 下发（M3 阶段引入，接口一致）。"""
```
三层一致：stub（纯逻辑/单测）-> SimEntity（unitree_mujoco，sim2real 校验）-> UnitreeReal（真机）。切换只改一处注入。

## 4.1 真机走哪条路：高层 SportClient（2026-08-29 定）

**结论：接真机优先用高层 `SportClient`，不要自己调低层步态。**

```
SportClient.Move(vx, vy, vyaw)     # 前/侧移 m/s，转向 rad/s
StandUp / StandDown / StopMove / BalanceStand / FreeWalk / ClassicWalk / Euler
```
狗自身的小脑已经实现了全向移动 + 转向（官方
`example/go2/high_level/go2_sport_client.py` 里就有 `Move(0,0,0.5)` 原地转）。
现在在 DDS 低层手调 trot 只能走直线，那是"从零造轮子" —— 真机上大概率用不上。

**但高层给的是"速度"不是"坐标"**，所以"走到某点"得自己闭环：

```
读位姿 → plan_drive() 算速度 → Move() 发出去 → 再读位姿 → …… → 到了就停
```

`robot/real_sport.py` 把这个闭环做成了两层：

| 部分 | 能不能现在验 |
|---|---|
| `plan_drive()` 纯函数（输入位姿+目标，输出速度；不碰硬件、不 sleep） | ✅ 有单测 |
| `RealSportEntity` 的超时 / 卡住放弃 / 急停收速 | ✅ 有单测（喂假狗积分位姿） |
| `connect_sport()` / `sportmode_pose_source()` 的连接代码 | ❌ 要真机 |

假狗实测收敛（dt=0.05，max 0.4m/s）：正前方 2m≈5s、掉头 2m≈9s、斜前方 (2,2)≈10s，
终点误差 ≤ arrive_tol(0.25m)。**增益（k_v / k_yaw）真机到手后要按实测重调。**

**两个已查证的坑：**
1. `unitree_mujoco` **不支持高层**：`UnitreeSdk2Bridge` 只订阅 `rt/lowcmd`，
   不响应 SportClient 的 RPC 请求 → 高层接口在仿真里验不了，只能"写好等真机"；
   仿真闭环仍走低层 DDS。
2. `SportModeState_` 里有 `position[3]` / `imu_state.rpy` / `velocity` /
   `range_obstacle[4]`（避障距离），**但没有电量** → `sportmode_pose_source()`
   故意不填 battery_pct，安全闸会按"电量未知"只放行 move_to（fail-closed）。
   真机到手要补 BMS 电量源，否则巡逻（navigate）会一直被拒。

**硬件门槛**：Go2 只有 X（基础支持）/ EDU（支持）开放二次开发，AIR / PRO 官方不开放
（宇树官网支持页，2026-08-29 查证）。买之前先确认型号。

## 5. 运动原语白名单 + 安全闸门（防篡改 / 真机安全）
```python
# primitives.py —— 对应 npc/reviewer.py::ALLOWED_TASK_ACTIONS 的机器人版
ALLOWED_MOTION_ACTIONS = ("move_to", "navigate", "grab", "release")
# 重申 npc 铁律：LLM 零关节/零文件直控；只允许白名单原语
FORBIDDEN_MOTION_TOKENS = {"file", "path", "write", "read", "exec", "shell", "open"}

# safety.py —— A 审查升级为真机安全闸门（参照 Claudia 三级电量 + 非绕过门）
class SafetyGate:
    def check(self, action, params, robot_state) -> tuple:
        # 1) 动作必须命中 ALLOWED_MOTION_ACTIONS
        # 2) 禁触字段/值 -> 拒
        # 3) 急停标志已置位 -> 全拒
        # 4) 电量门控：<=10% 仅安全原语 / <=20% 拒高能耗 / 正常全量
        # 5) 目标坐标必须在可达边界内 + 速度/力矩上限
```
SafetyGate.check 是不可绕过的（所有 RobotExecutor 调用先过它，同 npc 的"落账口不可绕过"思想）。B1 生成文案、B2 编译任务、A 审查 + 安全闸双重放行后才下发。

## 5.1 真机安全（上狗前必读 `机器人/真机安全清单.md`）

**软件急停是最后一道，永远不是第一道。** 软件挡不住：进程被杀、电脑蓝屏、
狗端死机、以及 15kg 狗已经冲出去之后的惯性。物理急停（遥控器）+ 有人在场才是第一道。

链路看门狗（`watchdog.py`）是软件侧补上的一个真实漏洞：

```
下发 Move(0.4, 0, 0) → 链路断了 → 狗收不到"停" → 沿 0.4 m/s 一直走下去
```
高层 `Move()` 是**持续生效**的，软件急停救不了这个场景（没人发得了），
所以必须有"多久没收到状态帧就自己停"的兜底。`LinkWatchdog` 跳闸后
**不会自动恢复**，必须显式 `reset()` —— 断过一次就该停下来等人来看。

配套：`real_sport.move_to` 整个循环包在 `try/finally` 里，任何异常都先收速再往外抛
（循环一崩没停 = 狗带着最后一条速度狂奔）。

## 7. 一次"指令 -> 执行"时序
```
用户文本/语音
  -> B2 compile_task()            （复用：机器人意图词表，扩展"巡检/拿/放/去房间"）
  -> A review_task()              （复用：可行性 + 白名单 + 禁触字段）
  -> SafetyGate.check()           （新建：真机安全，附加一关）
  -> 落账 book()->pending_task     （复用：唯一入口）
  -> RobotBackend.apply(步骤)      （通过 RobotExecutor -> stub/sim/real）
  -> 结果/新状态 -> perception -> 记忆回流（maybe_reflect/consolidate 复用）

急停（任意时刻，另一条路径）：
  POST /api/estop -> brain.estop() -> backend.estop()
      ├─ gate.set_estop()     闸门拒绝一切新动作
      └─ executor.estop()     通知执行器，让正在跑的长动作从内部退出
  （两条腿缺一不可：只置闸门 = 跑完当前那一段才停，真机上就是"急停后狗还往前冲"）
```

**test_estop_and_tick.py 是 2026-08-29 评审后新建的**，专门钉"跟时间有关"的 bug ——
stub 执行器是瞬移的，把所有时序问题都藏起来了，所以这里用"会耗时的假执行器"：
- 急停必须到达执行器，并能中断正在跑的长动作（P0-1）
- tick 不得阻塞事件循环，用心跳探针量**阻塞期间**的最大响应间隔（P0-2）
- 禁触字段递归扫描 / 电量未知 fail-closed / 坏记忆卡改名留证（P1）

这三条钉子都做过反向验证：把代码退回修复前的行为，它们会如期失败，不是空跑。

验证顺序：单测 stub -> sim 链路冒烟 ->（有真机后）sim2real 对照真机。
